## 1. Architecture

```
Marketing Website (monzerallan.com)         → WebApp            (unchanged)
Application UI (app.monzerallan.com)        → AppExperience      → PWA_WEB_APP / CAPACITOR_NATIVE
```

**IMPLEMENTED.** `src/App.tsx` branches once, at the root, on `getAppMode()`
(`src/hooks/use-native-platform.ts`):

```tsx
const appMode = getAppMode();
return appMode === "MARKETING_WEB" ? <WebApp /> : <AppExperience />;
```

`AppExperience` (renamed from `NativeApp` — `src/app-native/AppExperience.tsx`, same file, same 20
screens, same `src/app-native/` directory) is now rendered for **both** `PWA_WEB_APP` and
`CAPACITOR_NATIVE`. Nothing was duplicated: the existing 20 screens, `AppScreen` shell,
`BottomNavigation`, onboarding flow, deep-link/back handlers, and every service they call are reused
byte-for-byte between the installed Android/iOS app and the new Web App. The only new UI is a
desktop-only sidebar (§10) and a handful of small PWA-specific components (install card, offline
banner, update banner — §8/§20).

## 3. Hostname / Mode Detection

**IMPLEMENTED.** One central function, `getAppMode()` in `src/hooks/use-native-platform.ts`, decides
between the three environments — nothing else in the codebase branches on hostname or Capacitor
directly:

1. `CAPACITOR_NATIVE` — `Capacitor.isNativePlatform()` (or the existing native dev-preview flag).
2. `PWA_WEB_APP` — if the build was produced with `VITE_APP_MODE=pwa` (baked in via `.env.app`, read
   at runtime — see §5), **or** `window.location.hostname` starts with `app.` (covers
   `app.monzerallan.com` and any `app.*` staging subdomain), **or** the dev-only `?app-preview=true`
   flag is set (§4).
3. Otherwise `MARKETING_WEB`.

## 4. Dev Preview

**VERIFIED.** Visiting `http://localhost:5173/?app-preview=true` once sets a `localStorage` flag
(`__force_app_preview`, mirroring the existing `__force_native_preview` convention) that persists
across client-side navigation, where the query string itself would otherwise be lost on the first tab
click. Only active when `import.meta.env.DEV` is statically true — dead code, verified absent from
both production bundles by construction (same mechanism as the existing native-preview flag, already
audited in a prior phase). Verified with Playwright: the app experience renders correctly at both a
390×844 (mobile) and 1440×900 (desktop) viewport via this flag, with no real device/emulator needed.

## 5. Build Modes

**VERIFIED.**

| Command | Output | PWA plugin active | Manifest/SW present |
|---|---|---|---|
| `npm run build` / `npm run build:web` | `dist/` | No | No |
| `npm run build:app` | `dist-app/` | Yes | Yes |

`vite.config.ts` reads Vite's own `--mode` flag (`vite build --mode app`), which auto-loads
`.env.app` (`VITE_APP_MODE=pwa` — a public, non-secret presentation flag only, never used for any
security decision) and switches `build.outDir` to `dist-app`. The `VitePWA` plugin itself is only
added to the plugins array when `mode === "app"` — for the default build it never runs at all, which
is what guarantees zero PWA footprint in the marketing bundle (§2), not a runtime check. Both builds
were run and their outputs directly inspected in this session; `dist/` and `dist-app/` never share an
output directory. `npm run cap:sync` / `cap:sync:ios` / `cap:android` / `cap:ios` still call the plain
`build` script, so Capacitor's `webDir: "dist"` is untouched.

## 7. Service Worker

**VERIFIED (generation) / REQUIRES PRODUCTION DEPLOYMENT (real offline test over HTTPS).**
`vite-plugin-pwa`'s `generateSW` strategy produced `dist-app/sw.js` + `dist-app/workbox-*.js` in this
session. Registration is **hand-written** (`src/pwa/registerServiceWorker.ts`), not the plugin's
`virtual:pwa-register` helper — that virtual module only resolves when the plugin is active, and
importing it unconditionally would have broken the marketing build; the hand-written version is a
plain `navigator.serviceWorker.register()` call, guarded by `getAppMode() === "PWA_WEB_APP"` and
`!import.meta.env.DEV`, so it is inert everywhere else.

Verified directly by grepping the built `dist-app/sw.js`: `googleapis`/`gstatic` (Google Fonts) are
present as runtime-cached origins; **no** occurrence of `supabase.co` or `functions/v1` exists
anywhere in the file — Supabase Auth, REST, and every Edge Function (`ai-chat`, `food-scan`,
consultation booking, Stripe-adjacent calls) are never intercepted by the service worker, by
construction, not by a runtime exclusion rule that could be forgotten. Precache is scoped to app-shell
file types only (`js,css,html,ico,svg,png,woff2`); product photos/icons get a same-origin
`StaleWhileRevalidate` runtime cache instead of bloating the initial install.

## 14. Platform-Aware AI Actions (3-Way)

**VERIFIED.** `supabase/functions/_shared/actionRegistry.ts`'s `Platform` type is now
`"web" | "pwa" | "native"`. Because `pwa` and `native` always render the identical `AppExperience`
route tree, their destinations are defined **once** per concept (`ConceptConfig.app`) and mechanically
expanded to both `pwa` and `native` registry entries at module load (`buildRegistry()`) — it is
structurally impossible for the two to diverge by editing mistake. `web` genuinely differs per concept
and is configured separately. `getKnownRoutes()` (`_shared/knowledge-retrieval.ts`) and the Gemini
response schema / system-prompt instruction (`ai-chat/index.ts`'s `buildResponseSchema` /
`buildPlatformInstruction`) both already flowed generically on the `Platform` type and needed no
further change beyond accepting the third value.

`src/services/aiChatService.ts` now sends `platform: "native" | "pwa" | "web"` based on `getAppMode()`.

Verified with a standalone script (`tsx`, run against the real `actionRegistry.ts` file, not a copy)
asserting, for all 14 action concepts: `pwa` and `native` always resolve identically; `VIEW_FAQ`
resolves only on `web`; `OPEN_FOOD_SCANNER`/`OPEN_QIBLA`/`OPEN_PRAYER_TIMES`/`OPEN_AI` resolve only on
`pwa`/`native`; and a full `sanitizeActions()` pass for all three platforms correctly includes/excludes
platform-specific actions, always honors the known-route allowlist, and never exceeds the 3-action cap.
**15/15 assertions passed** (30+ individual checks across the three platforms). The Deno Edge Function
files were not independently re-typechecked with the Deno shim this session (already verified clean in
the prior AI Concierge phase; only the `Platform` union and two literal-comparison lines changed here).

## 15. Food Scanner

**VERIFIED (build) / IMPLEMENTED (runtime, browser camera untestable from this environment).**
`src/services/foodScanService.ts`'s `capturePhoto()`/`pickFromGallery()` now branch on
`isNativePlatform()`: native keeps calling `@capacitor/camera` exactly as before (byte-identical
behavior, confirmed by the Android Gradle build succeeding — §21); web/PWA uses a new
`pickImageViaFileInput()` adapter — a plain `<input type="file" accept="image/*">`, with

browsers never fire `change` when the visitor cancels the native picker, so a `window` `focus`-based
fallback resolves the promise instead of hanging forever, and the hidden input element is always
cleaned up. This is a genuine platform adapter, not a call to any Capacitor plugin from browser code.

## 23. Hostinger Deployment

**IMPLEMENTED — exact steps, using the folder names actually produced in this session.**

1. Run `npm run build:app` locally. This produces **`dist-app/`** — upload the **contents** of this
   folder (not the folder itself) to the document root for `app.monzerallan.com`.
2. In hPanel, create the subdomain `app.monzerallan.com` (Hostinger → Domains → Subdomains) if it

   step that must be confirmed against the actual hosting panel, since exact document-root conventions

   (generated by `scripts/write-app-htaccess.cjs`, §20) is already the correct one for this
   folder — do not copy the marketing site's `public/.htaccess` here, and do not copy
   `dist-app/.htaccess` into the marketing folder either; they intentionally differ (CSP is app-only).
4. Confirm DNS: `app.monzerallan.com` needs its own A/CNAME record pointed at Hostinger, separate from
   the existing `monzerallan.com`/`www` records, with SSL issued for the new subdomain (Hostinger's
   free SSL covers subdomains, but it must be provisioned for `app.` specifically once the subdomain is
   created).
5. Nothing about the existing `monzerallan.com` deployment changes — its folder, its `.htaccess`, and
   its build (`dist/`, from `npm run build` / `npm run build:web`) are all exactly as before this task.
