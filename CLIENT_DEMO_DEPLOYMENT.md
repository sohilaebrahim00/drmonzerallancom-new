# Client Demo Deployment — `demo.monzerallan.com`

This is a **completely separate build and deployment** from the real site. It shares source
code with `monzerallan.com` and `app.monzerallan.com`, but is compiled into its own isolated
output folder with no connection to the real Supabase project, no real authentication, and no
way to write to production data. See `src/dev/demoMode.ts` for the full technical safety
explanation.

## What to upload

**Folder to upload: `dist-demo/`**

Not `dist/` (that's `monzerallan.com`) and not `dist-app/` (that's `app.monzerallan.com`).
Upload the **contents** of `dist-demo/` — including the hidden `.htaccess` and `robots.txt`
files it contains — to the document root of the `demo.monzerallan.com` subdomain.

## 1. Build it

```bash
npm run build:demo
```

This runs `vite build --mode client-demo` (reading `.env.client-demo`, which deliberately
ships with **blank** Supabase credentials — this build cannot reach the real database even if
a code path were missed) and then `scripts/write-client-demo-assets.cjs`, which writes a
demo-specific `robots.txt` (`Disallow: /`) and `.htaccess` (SPA routing + a `noindex, nofollow`
HTTP header + a tight Content-Security-Policy) into `dist-demo/`.

Verify the build before uploading:

```bash
npx tsc --noEmit
npm run lint
npm run build:web    # confirm monzerallan.com's own build still succeeds, untouched
npm run build:app    # confirm app.monzerallan.com's own build still succeeds, untouched
npm run build:demo
```

## 2. Set up the subdomain on Hostinger

1. In hPanel, go to **Domains → Subdomains** and create `demo.monzerallan.com` if it doesn't
   already exist, pointing at a new, empty document root — e.g. `public_html/demo/` (do **not**
   point it at the same folder as `monzerallan.com` or `app.monzerallan.com`).
2. Wait for DNS/subdomain propagation to finish (usually a few minutes on Hostinger).

## 3. Upload

1. Open **File Manager** (or connect via FTP/SFTP) and navigate to the subdomain's document
   root (e.g. `public_html/demo/`).
2. Delete any placeholder `index.html`/default files Hostinger may have created there.
3. Upload the **entire contents** of your local `dist-demo/` folder — every file, including
   `.htaccess` and `robots.txt` (these start with a dot, so make sure your FTP client or File
   Manager is set to show hidden files).
4. Confirm the document root now directly contains `index.html`, `.htaccess`, `robots.txt`,
   and an `assets/` folder — not a `dist-demo/` folder nesting them one level deeper.

## 4. Verify

Visit:

- `https://demo.monzerallan.com/` → small "Dr. Monzer Allan / Client Preview" chooser with
  **View User Experience** / **View Doctor Experience** buttons.
- `https://demo.monzerallan.com/user` → redirects straight into the full authenticated user
  experience (Sarah Ahmed fixture data), no login required.
- `https://demo.monzerallan.com/doctor` → redirects straight into the full doctor experience
  (Dr. Monzer Allan fixture data, patient list), no login required.
- Refresh the page on any in-app screen (e.g. after navigating to Program or Social) — it must
  **not** 404. If it does, the `.htaccess` didn't upload correctly (re-check step 3) or
  `mod_rewrite` isn't enabled on the hosting plan (contact Hostinger support — it's enabled by
  default on all standard Hostinger shared/business plans).
- Open the browser dev tools Network tab while browsing — there should be **zero** requests to
  any `supabase.co` domain and zero requests to any AI/Gemini endpoint.

## 5. Sending the links to the client

Send exactly these two links — they're the only ones a client should need:

```
https://demo.monzerallan.com/user
https://demo.monzerallan.com/doctor
```

Both land the client directly in the relevant experience with no query parameters to type and
no account to create. A small fixed "Client Preview — Sample Data" bar (with a one-tap switch
between the two views) stays visible throughout, and a line near the chooser and account/profile
areas states plainly that live account and health data are not connected — a client should never
mistake the sample data shown here for a real account's data.

## 6. Search engine protection

This subdomain is deliberately **not indexed**:

- `dist-demo/robots.txt` (generated by the build, not the shared `public/robots.txt` used by
  `monzerallan.com`) contains `Disallow: /` for all crawlers.
- `dist-demo/.htaccess` sends an `X-Robots-Tag: noindex, nofollow` HTTP header on every
  response — this covers crawlers that ignore `robots.txt` or that request a resource directly
  without first checking it.
- The app also injects a `<meta name="robots" content="noindex, nofollow">` tag at runtime for
  any crawler that executes JavaScript.

No action needed — this is all baked into the build. Just don't link to
`demo.monzerallan.com` from the real marketing site, sitemap, or any indexed page.

## 7. Optional access protection

The demo build has **no application-level password** — implementing a fake client-side
JavaScript password prompt would not be real security (anyone can view the page source and
bypass it), so one was deliberately not built. If you want to restrict who can open the link
before you're ready to share it, use Hostinger's **hosting-level** protection instead:

### Option A — Hostinger's Directory Password Protection (recommended if available)

1. In hPanel, go to **Advanced → Password Protect Directories** (also sometimes listed as
   just **Password Protection** under the domain's tools).
2. Select the `demo.monzerallan.com` document root directory.
3. Set a username and password. Hostinger implements this as standard Apache HTTP Basic Auth
   (a real `.htpasswd`/`.htaccess` `AuthType Basic` mechanism enforced by the web server itself,
   not by client-side JavaScript) — a browser will show a native username/password prompt before
   serving *any* file in that directory, including `index.html`.
4. Share the username/password with the client alongside the two links above.

If this exact panel option isn't available on your specific Hostinger plan, the equivalent can
be requested from Hostinger support, or configured manually by adding an `AuthType Basic` block
referencing a `.htpasswd` file to the top of `dist-demo/.htaccess` (do this by hand-editing the
uploaded copy on the server, not the generated source — re-running `npm run build:demo` will
regenerate `.htaccess` from `scripts/write-client-demo-assets.cjs` and overwrite a manual edit
on your next deploy, so keep a note of the change and re-apply it after each redeploy, or ask
to have this password block added to that script if it becomes a permanent requirement).

### Option B — No hosting-level protection available

If your Hostinger plan doesn't offer directory password protection, it's acceptable to leave
`demo.monzerallan.com` as an **unlisted preview URL**: it is not linked from anywhere indexed,
not in any sitemap, and blocked from search engines (see §6) — so in practice only someone who
has been given the exact link can reach it. This is a real, commonly-used tradeoff (the same
one used by most "preview deployment" services), but it is **not** the same guarantee as a
password — document this choice for the client so expectations are clear (anyone who obtains the
link, e.g. by having it forwarded, could open it) if you go this route instead of Option A.

## What this build structurally cannot do

- **Cannot write to the real Supabase database.** `.env.client-demo` ships with blank
  `VITE_SUPABASE_URL`/`VITE_SUPABASE_PUBLISHABLE_KEY`, so the Supabase client is never even
  created in this build (`src/lib/supabase.ts`'s `isSupabaseConfigured` is `false`) — on top of
  every data-fetching function already short-circuiting to fixture data before it would ever
  touch Supabase (see `src/dev/demoMode.ts`).
- **Cannot call Gemini.** The photo-scan flow in this build skips the camera and the real
  Edge Function entirely, jumping straight to a fixed synthetic result labelled
  "Demo preview result — not a real Gemini analysis."
- **Requires no login.** `AuthContext` substitutes a fixed fake identity (Sarah Ahmed or
  Dr. Monzer Allan, depending on which view is active) instead of running real Supabase auth.
- **Cannot affect `monzerallan.com` or `app.monzerallan.com`.** Those are built by
  `npm run build:web` / `npm run build:app` respectively — completely separate `vite build`
  invocations, completely separate output folders (`dist/`, `dist-app/`), and verified (via a
  build-time resolver-alias swap, plus a post-build grep of the output) to contain **zero**
  demo fixture data or client-demo code, dead or otherwise.
